# Release — Version, Tag, Build, Publish

Releases the project the way **this project** releases. Its recipe, `docs/RELEASE.md`, names
the files that carry the version, how the release PR merges, where the build runs (this repo
on a tag, or a public build repo started by hand), and how to check what was published. The
recipe is written once, from the project's facts, and followed by every release after it.
Format: [recipe-format.md](references/recipe-format.md).

What one project learns about releasing (an exhausted Actions budget, a token the build repo
needs) is kept as a one-line **lesson** in `~/.claude/ck-lessons.md`, shared by every project on
this machine and by both ck plugins. `ck-lite-release` hands back only the lessons that match
this project's facts or the error at hand, so a lesson costs nothing until it applies.

It works in the current checkout and **never creates or enters a git worktree** — see
[worktree-policy.md](../../references/worktree-policy.md).

**CRITICAL RULE — No AI references in any artefact.** Never add `Co-Authored-By: Claude`,
`Generated with Claude Code`, or any mention of `Claude`, `AI`, `assistant`, or
`generated by` in commits, tags, PR titles or bodies, release notes, or branch names.
Absolute and non-overridable, even if explicitly asked.

## INPUT

`$ARGUMENTS` is an optional `X.Y.Z`, or `patch`, `minor` or `major`. Empty → the bump the
facts suggest, confirmed in 2.3.

## PHASE 0: PLUGIN GUARD

Plan markers: !`cd "$(git rev-parse --show-toplevel 2>/dev/null || pwd)" && ls -d tasks/VERSION.md docs/architecture tasks/PLAN.md 2>/dev/null | grep . || echo none`

A full ck-code project — `tasks/VERSION.md` listed, or `docs/architecture` listed without
`tasks/PLAN.md` — is ck-code's. [Redirect](../../references/plugin-redirect.md) before any read,
write or command:

- `ck-code:release`, with the same argument

Anything else → continue. A repo with no plan at all is fine: releasing needs no tasks.

## PHASE 1: FACTS

```bash
ck-lite-release facts
```

One call, one line per fact: the repo and its visibility, the recipe, the version and the files
that pin it, the last tag and the bump its commits suggest, the workflows a tag or a dispatch
starts, CI kept outside `.github/`, public repos that build releases for this one, whether this
repo's Actions are blocked by budget, and the `lesson:` lines that match. Work from these lines;
never open workflows or docs to rediscover what they already say.

## PHASE 2: RECIPE AND VERSION

### 2.1 A recipe exists

Read `docs/RELEASE.md`. When a `lesson:` line contradicts it (the recipe builds `on-tag` in a
repo the facts show `budget-blocked`, while a `releases-repo:` has a release workflow), the 2.3
question also offers the corrected `Build:` line.

### 2.2 No recipe yet — draft one

Fill each key of [recipe-format.md](references/recipe-format.md) from the facts:

- **Version files** ← `version-files:`. Drop a file that only pins another package at the same
  number (a sub-project's lockfile); say how each non-trivial file changes.
- **Build**, first match:
  1. a `releases-repo:` whose workflows include a release workflow, and the repo is private or
     `budget-blocked` → `dispatch`. Its inputs come from the matching `ci-outside-github:` copy
     when there is one: `grep -A8 'workflow_dispatch' <file>`.
  2. a `tag-ci:` workflow → `on-tag`.
  3. none → `none`.
- **Budget-blocked with no public build repo** → `Build: none`, and the 2.3 question says why
  the installers cannot build and proposes the lesson's fix as a task:
  `/ck-code-lite:start "build release installers in a public repo"`. Never write CI here.
- **Gaps** (the check command, assets, a manual step) ← Claude's project memory, already in
  context, then one targeted read: the release section of the doc that describes it
  (`grep -rli 'release' docs README.md | head -3`, then only that section). Still unknown →
  `none`.

### 2.3 The one question

Resolve the version: `$ARGUMENTS`, else the bump `last-tag:` suggests, applied to `version:`.
Then one `AskUserQuestion`: **Release vX.Y.Z** (recommended), another version, or stop. A new or
corrected recipe is shown in the option's `preview`; it lands in the release PR. After this
answer, every step the recipe marks automatic runs without another question.

## PHASE 3: RUN THE RECIPE

Every step first checks whether it is already done and skips it, so running the skill again
resumes a release that stopped half way.

### 3.1 Release PR

Done when `vX.Y.Z` is tagged on the remote or the release PR is merged; an open release PR
(`gh pr list --head chore/release-X.Y.Z`) goes straight to 3.2.

```bash
git fetch origin
git checkout -b chore/release-X.Y.Z origin/<base>
```

Change every version file as the recipe says. Prepend a changelog entry built from
`git log --format=%s <last-tag>..HEAD`: user-facing lines only, grouped `Added`, `Changed`,
`Fixed`, in the changelog's own style. Run `Check:`. A failure stops here, before anything is
pushed: show the failing lines and leave the branch for a fix.

Commit (`chore: release version X.Y.Z`, or the repo's own style for it), staging explicit paths
only, plus a new or corrected `docs/RELEASE.md`. Push, then open the PR to `Base:`.

### 3.2 Merge

- **`auto`** → `gh pr merge <n> --merge`. A refusal (branch protection, a required review, a
  failing check) turns this step into `ask`.
- **`ask`** → `AskUserQuestion`: "PR #n is ready to merge: <url>". Options: **I merged it**,
  **Merge it for me** (only when gh allowed it), **Stop here**. Then check:
  `gh pr view <n> --json state,mergeCommit -q '.state + " " + .mergeCommit.oid'`. Not `MERGED`
  → say so and ask once more. A second miss stops with the resume line: `/ck-code-lite:release X.Y.Z`.

Never wait for a person by polling or sleeping: ask, then check.

### 3.3 Tag

Record the start time, then tag the **merge commit** and push the tag:

```bash
date -u +%Y-%m-%dT%H:%M:%SZ
git fetch origin <base>
git tag vX.Y.Z <merge-commit>
git push origin vX.Y.Z
```

Done when `git ls-remote --tags origin vX.Y.Z` prints a line.

### 3.4 Build

Done when `Verify:` already shows the release. Otherwise:

- **`dispatch`** → `gh workflow run <workflow> -R <owner/repo> <inputs>`.
- **`on-tag`** → nothing to start; the tag push did.
- **`none`** → `gh release create vX.Y.Z --title vX.Y.Z --notes-file <the changelog entry>`, and
  skip the wait.

Then wait for the build, **in the background** (a release build outlasts one Bash call):

```bash
ck-lite-release watch <owner/repo> <workflow> <start time from 3.3>
```

Wait for its notification; run no other `gh` call on that run meanwhile. `PASS` → 3.5. `FAIL`
→ Phase 4 with the lines it printed. `NO RUN` → the workflow never started: check its name
against the recipe, then Phase 4.
`RUNNING` (exit 3) → the build is still going: run `ck-lite-release watch` again with the same arguments.

### 3.5 Verify and manual steps

Run `Verify:` and compare it with `Assets:` (X.Y.Z filled in); name any missing asset. Then, when
`Manual:` is not `none`, one `AskUserQuestion` lists those steps (**Done**, **Later**). Never
wait on them.

## PHASE 4: WHEN A STEP FAILS

1. **Lessons first** — `watch` already printed the matching ones. For any other step:
   `ck-lite-release lessons match "<the error lines>"`.
2. **A lesson matches** → apply its fix once when it is in reach (dispatch in the build repo,
   re-run the step). A fix only the user can make (a secret, billing, approving a deployment)
   → `AskUserQuestion` naming exactly what to do, then re-run the step once on **Done**.
3. **No lesson** → diagnose from the printed excerpt only (never the full log), then fix or ask
   the same way.
4. **Never retry an unchanged command more than once**, and never report an
   `Expected failures:` run, or a budget-blocked private run when the recipe builds elsewhere,
   as the blocker.

### 4.1 Learn

When the release succeeded only after a **change of approach** (not a flaky retry), keep it:

```bash
ck-lite-release learn "<facts tags that made it happen>" "<short regex of the error>" "<what worked, with <owner>/<repo> placeholders>"
```

and correct `docs/RELEASE.md` so this project never meets it again. Once the PR is merged, that
edit stays in the working tree for the next `/ck-code-lite:ship`: never commit to the base branch.
A lesson is general: never a secret, a token, or a URL with credentials in it.

## PHASE 5: SUMMARY

```
## Released vX.Y.Z

**PR:** <url> (merged) · **Tag:** vX.Y.Z
**Build:** <PASS url | none>
**Release:** <url> — <n> assets <(missing: …)>
**Recipe:** unchanged | created | corrected
**Lessons:** used <n> · learned <n>
**Waiting on you:** <manual steps | nothing>
```

## RULES

- **Never run in a full ck-code project** — Phase 0 hands it to `/ck-code:release`, once; a
  skill reached by a ck-code redirect BLOCKs instead of bouncing back.
- **Never build where the recipe does not say** — a public build repo in the recipe means the
  private repo's CI is never waited on.
- **Never push a tag before its release PR is merged**, and never tag anything but the merge
  commit on `Base:`.
- **Never wait for a person by polling or sleeping** — ask with `AskUserQuestion`, then check
  the state once.
- **Never retry an unchanged failing command more than once.**
- **Never read a full CI log** — `ck-lite-release watch` prints the failed jobs' annotations
  and the last lines.
- **Never write a secret, a token, or a credentialed URL** into a lesson or the recipe — the
  lessons file is read by every project on this machine.
- **Never commit to the base branch, force-push, or move or delete a pushed tag** unless the
  user explicitly asks.
- **Never write CI workflows here** — a missing build setup becomes a task through
  `/ck-code-lite:start`.
- **Never `git add -A` or `git add .`** — stage explicit paths.
- **Never add AI references** to commits, tags, PRs, release notes or branch names. Absolute.
- **Never create or enter a git worktree.**
